a."จากแนวคิด 'Software Entropy' และ 'Broken Window Theory' ลองมองย้อนกลับไปในโปรเจกต์ที่คุณเคยทำ มี 'หน้าต่างที่แตก' บานไหนที่คุณเคยปล่อยปละละเลย และมันส่งผลกระทบอย่างไรในระยะยาว?"

Answer:
ละเลยการทำความสะอาดโค้ด Code Smells:ปล่อยให้มีฟังก์ชันที่ยาวเกินไป ไม่มีการเขียน

Unit Tests: มีโค้ดบางส่วนที่ไม่มีการทดสอบ ส่งผลให้มาตรฐานของทั้งโปรเจกต์ลดลง

การละเลย Bug เล็กน้อย: มีบั๊กการแสดงผลเล็กๆ หรือคำเตือน (Warning) ตอน Compile ที่ไม่มีผลกับระบบหลัก แต่ถูกปล่อยทิ้งไว้ไม่แก้ไข

ละเลยเอกสาร (Documentation): การไม่อัปเดต README หรือเอกสาร API ให้ตรงกับปัจจุบัน ทำให้คนในทีมเริ่มใช้วิธีการคาดเดาหรือลองผิดลองถูก

b."อธิบายหลักการ 'Take Responsibility' ในความเข้าใจของคุณ และยกตัวอย่างสถานการณ์ที่คุณจะนำหลักการ 'Provide Options, Don't Make Lame Excuses' ไปใช้ในการสื่อสารกับเพื่อนร่วมทีมในโปรเจกต์นี้"

Answer: สำหรับผมหลักการ Take Responsibility คือการยอมรับความรับผิดชอบต่อหน้าที่และผลลัพธ์ของงานที่ได้รับมอบหมาย ไม่โทษผู้อื่นหรือหาข้ออ้างเมื่อเกิดปัญหา แต่กล้ายอมรับข้อผิดพลาด พร้อมหาวิธีแก้ไขและป้องกันไม่ให้เกิดซ้ำ

สมมติว่าผมได้รับมอบหมายให้พัฒนาฟีเจอร์หนึ่งของโปรเจกต์ แต่พบว่าต้องใช้เวลามากกว่าที่คาดไว้จนไม่สามารถส่งงานได้ตามกำหนด แทนที่จะบอกเพียงว่า "ทำไม่ทันเพราะงานยาก" หรือ "ติดธุระ" ผมจะสื่อสารกับเพื่อนร่วมทีมอย่างตรงไปตรงมา ผมจะบอกกับเพื่อนร่วมทีมว่าจะส่งส่วนที่ทำเสร็จก่อนเพื่อให้ทีมสามารถทำงานต่อได้
