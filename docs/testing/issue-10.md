# Issue #10 — โน้ตและแฟลชการ์ดข้ามอุปกรณ์

เกณฑ์: https://github.com/Software-Engineering-Concepts-2026/se-sec2-team-07/issues/10

## พฤติกรรม

ใช้ PostgreSQL กลางเดิม บัญชีเดียวกันบนเว็บไซต์/ฐานข้อมูลเดียวกันเห็นข้อมูลที่บันทึกแล้ว หน้า Dashboard/Library/Editor/Notes ตรวจข้อมูลทุก 30 วินาทีเมื่อมองเห็นหน้า และเมื่อกลับเข้าแท็บหรือออนไลน์ มีปุ่มดึงข้อมูลล่าสุดและสถานะการซิงค์ การซิงค์เป็น GET ไม่สร้างข้อมูลใหม่

Editor/Notes พักการดึงข้อมูลขณะมีร่างหรือกำลังบันทึก หากต้องการดึงทับร่างต้องยืนยันก่อน ร่างจะถูกแทนที่เมื่อโหลดสำเร็จเท่านั้น หากโหลดล้มเหลวยังเก็บข้อมูลเดิมพร้อมแสดงข้อผิดพลาด เมื่อเปลี่ยนรหัสชุด/โน้ตผ่านการนำทางจะไม่ใช้ร่างต้นทางไปบันทึกปลายทาง

การแก้ไข/ลบจากหน้าจอส่ง revision ถ้าอีกอุปกรณ์บันทึกไปก่อน API ตอบ 409 และคงร่างไว้ ให้คัดลอกส่วนที่ต้องการเก็บก่อนดึงข้อมูลล่าสุด ไม่รวมการแก้ไขชนกันให้อัตโนมัติ

POST/PUT จาก Editor/Notes ใช้ request_id เดิมเมื่อยังไม่ทราบผลการบันทึกจาก network/5xx ช่องแก้ไขถูกพักไว้จนกดบันทึกซ้ำเพื่อยืนยันคำขอเดิมสำเร็จ ข้อมูลและใบรับคำขอบันทึกใน transaction เดียวกัน แยกตามเจ้าของและชนิดข้อมูล คำขอซ้ำไม่เพิ่ม revision/การ์ด/โน้ตซ้ำ แม้ต้นฉบับถูกลบหลังบันทึกแล้วก็ไม่สร้างกลับเอง

## ข้อจำกัดและการใช้งานจริง

- ยังไม่ได้ deploy เว็บไซต์กลางหรือทดสอบมือถือจริงสองเครื่อง ต่าง session ใน Chrome ใช้ทดแทนการตรวจบัญชีและข้อมูลร่วมกันเท่านั้น localhost ของแต่ละเครื่องไม่ใช่เซิร์ฟเวอร์เดียวกัน
- ไม่มี offline queue, autosave ร่าง, push แบบทันที หรือการเก็บคำขอค้างข้าม reload/ปิดแท็บ ให้คงหน้าไว้แล้วกดบันทึกซ้ำเมื่อยังไม่ทราบผล หากออกไปแล้วให้ตรวจคลังก่อนสร้างใหม่
- API รองรับ client รุ่นเก่าที่ไม่ส่ง revision/request_id แต่จะไม่ได้การป้องกัน stale write/dedup แบบหน้าจอใหม่
- ใบรับคำขอเก็บจนลบบัญชี ยังไม่มี retention/งานเก็บกวาดหรือ load test ผู้ใช้จำนวนมาก
- ไม่ซิงค์ตำแหน่งการ์ดที่กำลังทบทวน/Pomodoro หรือร่างที่ยังไม่บันทึก; หน้า Review ไม่ถูกสลับการ์ดกลางรอบ
- การออกจากระบบยังเพิกถอน session ทุกอุปกรณ์ตามระบบเดิม
- ข้อจำกัด live AI, เอกสารซับซ้อน และ PDF ภายใต้โหลดจากงานก่อนหน้ายังคงอยู่

## ฐานข้อมูลและการย้อนกลับ

migration `005_sync.sql` เพิ่ม revision ใน decks/notes และตาราง sync_receipts โดยไม่เปลี่ยนข้อมูลเดิม Startup ใช้ migration ตามเดิม ไม่แก้ migration ที่ใช้ไปแล้ว การย้อน frontend/backend ต้องคงคอลัมน์/ตารางนี้ไว้; โค้ดเก่าไม่เพิ่ม revision จึงไม่ควรรัน mixed writer ระหว่าง rollout หากต้องย้อน schema ต้องวางแผน migration ใหม่และสำรองข้อมูลก่อน
